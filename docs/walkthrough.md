# Разбор: от журнала до обоснованного вывода

Сценарий полностью синтетический: магазин работает 90 минут, на 45–54-й минутах
у оплаты растут ошибки и задержки. Проверим, что можно заключить из отчёта,
а где ограниченная память требует осторожности. Нужны уже собранный LogScope
и Python; [сборка описана в README](../README.md#быстрый-запуск).

Команды ниже — для Bash из корня проекта. `set -e` останавливает последовательность
при ошибке; каждый раз создаётся новый каталог. На Windows имя бинарника —
`build/logscope.exe`; для PowerShell используйте отдельные шаги с проверкой
`$LASTEXITCODE`, как в [примере адаптера](NGINX.md#сначала-преобразование-затем-анализ).

```bash
set -e
demo=$(mktemp -d build/walkthrough.XXXXXX)
bin=./build/logscope
python scripts/generate.py --output "$demo/data" --requests 10000 --seed 2026 --cardinality 64
"$bin" analyze "$demo/data/incident.tsv" --baseline "$demo/data/baseline.tsv" --strict --capacity 128 --top 10 --json > "$demo/report.json"
python scripts/render_html.py "$demo/report.json" --output "$demo/report.html"
```

## 1. Сначала проверяем качество и точные итоги

Генератор сразу пишет строгий TSV и независимые итоговые счётчики `data/truth.json`.
`report.html` открывается локально без сервера. В JSON для обоих периодов должны
быть `input.rejected=0`, `input.accepted=10000`; сравните `summary` с `truth.json`:

| Показатель | Инцидент | Базовый период |
|---|---:|---:|
| Запросов | 10000 | 10000 |
| Ответов 5xx | 305 | 94 |
| Байтов тела | 62489129 | 63651649 |
| Сумма задержек, мкс | 459797928 | 236764840 |

Для этого набора доля ошибок выросла с 0,94% до 3,05%: `error_rate_delta_pp=2.11`.
Средняя задержка стала примерно в 1,942 раза больше. В `alerts` — десять минут
от 00:45 до 00:54 UTC 1 января 2026 года. Это согласуется с заложенным сценарием,
но сам сигнал не доказывает причину реального сбоя. Оба периода здесь равной
длительности; `request_ratio=1` вообще не является показателем запросов в секунду.

Счётчики и сумма задержек точны. Для p95 выводится **интервал** `[32768,65535]`
мкс: нельзя записать в заключении «p95 точно 65535». Интервал содержит квантиль
ближайшего ранга; [подробный контракт](SPEC.md) объясняет способ расчёта.

## 2. Если исходный журнал — наш профиль Nginx

Это отдельный маленький пример импорта, а не другой формат генератора выше.
Создайте две синтетические строки собственного [профиля](NGINX.md):

```bash
cat > "$demo/nginx.jsonl" <<'JSON'
{"msec":"1767225600.001","request_method":"GET","request_uri":"/catalog?campaign=synthetic","status":"200","body_bytes_sent":"100","request_time":"0.010"}
{"msec":"1767225600.002","request_method":"POST","request_uri":"/checkout?campaign=synthetic","status":"503","body_bytes_sent":"20","request_time":"0.250"}
JSON
python scripts/nginx_to_tsv.py "$demo/nginx.jsonl" > "$demo/nginx.tsv"
"$bin" analyze "$demo/nginx.tsv" --strict --json > "$demo/nginx-report.json"
```

При успехе адаптер сообщает две преобразованные строки, ноль отклонённых и код 0.
В TSV пути `/catalog` и `/checkout` уже без query; задержки — 10000 и 250000 мкс.
В отчёте: 2 запроса, 1 ответ 5xx, 120 байт, сумма задержек 260000 мкс.
Перевод секунд не добавил микросекундной точности: исходное разрешение — 1 мс.
При любой ошибке адаптера нельзя анализировать его частичный префикс; даже
`--skip-invalid` возвращает ненулевой код, если были повреждённые записи.

Профиль проверен также настоящим Nginx 1.30.6 в
[CI для 39b0038](https://github.com/GrantCanyon/logscope/actions/runs/41365469742):
`nginx -t` и шесть HTTP-запросов → журнал → адаптер → C. Этот локальный разбор
не запускает Docker и не заменяет проверку конфигурации вашего сервера.

## 3. Как маленькая таблица способна ввести в заблуждение

```bash
"$bin" analyze "$demo/data/incident.tsv" --strict --capacity 1 --top 1 --json > "$demo/small.json"
"$bin" analyze "$demo/data/incident.tsv" --strict --capacity 128 --top 128 --json > "$demo/exact.json"
```

В `small.json` единственный `top_requests` — `GET /catalog/item/47`:
`lower=1`, `upper=10000`, `error=9999`. Если прочитать верхнюю границу как частоту,
получится ложное впечатление, что весь трафик шёл на этот товар. На самом деле
в `exact.json` у него **111** запросов, а лидер — `POST /checkout` с **2097**.

Все 65 ключей помещаются в ёмкость 128: у каждого `lower=upper`, `error=0`.
При ёмкости 1 лидер был вытеснен; гарантированный интервал остался верным,
но ранжирование оказалось бесполезным. Точные общие итоги при этом не изменились.
`--top` ограничивает только число показанных строк; **память и точность определяет
`--capacity`**. Уменьшение одного лишь `--top` не вызывает описанного вытеснения.

## 4. Сопоставляем точность и память на том же потоке

Укажите действительные компилятор, версию и флаги своего бинарника в описании:

```bash
python scripts/accuracy.py --binary "$bin" --requests 10000 --cardinalities 64 --capacities 1,16,128 --top-k 10 --seed 2026 --repeats 3 --compiler-description "УКАЖИТЕ СВОЙ КОМПИЛЯТОР, ВЕРСИЮ И ФЛАГИ" --output "$demo/accuracy.json"
python scripts/render_accuracy.py "$demo/accuracy.json" --output "$demo/accuracy.html"
```

Для всех трёх ёмкостей используется один файл, совпадающий с `incident.tsv` выше.
В проверенном запуске SHA256:
`623990e37e7ce8c8a19ccb7121ae866efafe1a988256b4eec52f3670d781bafb`.
Независимый Counter проверяет и отслеживаемые, и пропущенные ключи двух потоков.

| Ёмкость | Максимальная ширина интервала частоты, все запросы | Совпадение с точным top-10 |
|---:|---:|---:|
| 1 | 9999 | 0% |
| 16 | 526 | 10% |
| 128 | 0 | 90–100% |

Последние 90–100% не означают неточность частот: на границе top-10 два ключа
имеют по 136 запросов, и допустимы разные точные десятки. Это диапазон при
разрешении ничьей, а не доверительный интервал. Для потока 5xx метрики отдельные.

HTML также показывает время и пиковую память отдельного процесса C, без памяти
Python Counter. На таком коротком входе базовая стоимость процесса и шум могут
скрывать разницу ёмкостей; не ожидайте строго монотонной кривой времени/RSS.
Фоновые процессы локального запуска не отключались, нагрузка не контролировалась.
Числа выше проверены на Python 3.12.14, Zig 0.17.0 cc, C17 -O2; время и память
другого окружения могут отличаться. Методика и более крупный сохранённый запуск —
в [ACCURACY.md](ACCURACY.md), измерения объёма входа — в [BENCHMARK.md](BENCHMARK.md).
