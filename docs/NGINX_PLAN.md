# Контракт и план: адаптер профиля LogScope для Nginx

Статус: контракт утверждён ведущим агентом. Адаптер реализован; локальные
и независимые проверки пройдены. Реальная контейнерная проверка ожидает CI.
Цель — практический потоковый импорт конкретного профиля. Универсальная схема
JSON Nginx не заявляется, основной C CLI не меняется. Python 3.10+, только stdlib.

## Основание и точный профиль

Первичные источники:
[log_format и escape=json](https://nginx.org/en/docs/http/ngx_http_log_module.html#log_format),
[переменные HTTP](https://nginx.org/en/docs/http/ngx_http_core_module.html#variables).
Nginx позволяет задавать формат. $msec — время записи журнала, а не начала запроса;
$request_time имеет миллисекундное разрешение. $request_uri сохраняет исходный URI
с аргументами; $body_bytes_sent исключает заголовки ответа.

Файл `examples/nginx/logscope-json.conf` содержит только определение в
контексте http; подключение access_log описывается отдельно:

```nginx
log_format logscope_json_v1 escape=json
    '{"msec":"$msec","request_method":"$request_method",'
    '"request_uri":"$request_uri","status":"$status",'
    '"body_bytes_sent":"$body_bytes_sent","request_time":"$request_time"}';
```

Здесь используются ровно шесть строковых полей, а не JSON numbers.
Порядок ключей неважен. Повторные, отсутствующие и дополнительные ключи отклоняются;
null, bool, массивы, объекты и числовые JSON значения вместо строк не принимаются.
Поля с пустой строкой или '-' не подменяются нулём. Отдельного поля version нет:
имя log_format и документация определяют версию профиля.

## Числа, время и точность

Числовые строки канонические ASCII: `0` либо ненулевая цифра и следующие цифры.
Без знаков, пробелов, экспоненты, запятой и ведущих нулей. Время дополнительно
имеет ровно три цифры после точки: `(0|[1-9][0-9]*)\.[0-9]{3}`.
Это грамматика нашего профиля; её фактическую совместимость проверит Nginx CI.

- `epoch_ms = seconds*1000 + milliseconds`, результат <= UINT64_MAX.
- `latency_us = (seconds*1000 + milliseconds)*1000`, результат <= 86400000000.
  Например, 0.123 → 123000 мкс; дополнительная точность не выдумывается.
- `body_bytes_sent` <= UINT64_MAX; status — 100..599.
- Метод — 1..16 заглавных ASCII-букв, как требует C CLI.

Преобразование только целочисленное, без float/округления. Перед int ограничивается
число цифр: строка из тысяч цифр внутри разрешённой строки даёт контролируемую
ошибку, а не traceback ограничения Python. $msec описывает конец обработки/запись
лога; нельзя представлять полученную минуту как время начала запроса.

## URI и query: утверждённая политика

Сначала проверяется весь декодированный JSON URI: 1..2048 видимых ASCII-символов,
начинается с '/' либо равен ровно '*'. NUL, tab, CR/LF, другие управляющие символы,
DEL, Unicode и непарные суррогаты отклоняются, в том числе внутри query.
Процентное декодирование не выполняется: буквальный `%0A` остаётся `%0A`.

**По умолчанию query удаляет адаптер до выдачи TSV.** Это не оставляет query
в промежуточном файле/потоке. Проверка полного URI до удаления не позволяет скрыть
повреждённую строку безопасным префиксом. `--keep-query` адаптера сохраняет query;
для сохранения query в группировке C также требуется его собственный --keep-query.
Ядро продолжает свою прежнюю политику группировки; восстановить удалённый query
оно не может. Ограничение полного исходного URI в 2048 символов намеренное,
даже если один путь после удаления длинного query оказался бы короче.

## Поток, ошибки и коды завершения

Команда: `python scripts/nginx_to_tsv.py INPUT|- [--keep-query] [--skip-invalid]`.
Один файл либо stdin на вызов, ASCII TSV v1 на stdout, без заголовка.
Окончания LF/CRLF и последняя незавершённая строка допустимы; одиночный CR в EOF
отклоняется. Пустой файл корректен, пустая строка — ошибка JSON.

Максимум 16384 байта на JSON-строку без окончания строки. Чтение бинарное,
с ограниченным readline/дочитыванием остатка блоками. В обычном случае память
ограничена одной такой строкой и JSON-объектом; слишком длинная строка не копится.
Вложенный JSON до лимита контролируемо отклоняется, включая RecursionError.
Счётчики/номер строки ограничены uint64; переполнение — контролируемая ошибка.

По умолчанию первая неправильная строка прекращает работу с кодом 3.
`--skip-invalid` дочитывает поток, выдаёт корректные записи, но при любом отклонении
тоже возвращает 3. Коды: 0 — всё преобразовано, 1 — параметры, 2 — ввод/вывод,
включая broken pipe, 3 — данные/лимиты. Ошибка чтения/записи приоритетнее кода 3.
Диагностика содержит только номер и фиксированный код причины; не более восьми
примеров и итоговые счётчики. Содержимое строки, значения полей, пути и тексты
исключений/traceback не выводятся. Коды причин фиксированы, например json,
encoding, fields, duplicate_field, field_type, number, timestamp, method,
target, status, bytes, latency, line_too_long, counter_overflow, io_read, io_write.

Потоковый адаптер не может отозвать уже выданный префикс после поздней ошибки.
Документация рекомендует сначала преобразование во временный TSV, проверку кода,
затем C-анализ. Для прямого Bash-конвейера обязательно `set -o pipefail`; результат
C нельзя принимать при ненулевом статусе любого участника. Для PowerShell —
раздельные шаги с проверкой $LASTEXITCODE. В тестах это проверяется явно.

## API и план проверки

Файлы: `scripts/nginx_to_tsv.py`, `tests/test_nginx_adapter.py`,
`examples/nginx/logscope-json.conf`, `tests/nginx_smoke.py`, `docs/NGINX.md`,
дополнение README и отдельный Linux job в существующем CI.
API: `convert_record(payload: dict, keep_query=False) -> str`,
`parse_line(raw: bytes, keep_query=False) -> str`, `AdapterError(reason)`.

1. RED fixtures QA: точные границы чисел, 0.001/24h, integer overflow, missing/'-',
   duplicate keys, неизвестные поля, JSON types, query/control/surrogate,
   overlong drain, открытый stdin, отсутствие секретов в stderr, broken pipe.
2. Реализовать адаптер до GREEN. Сверять выдаваемый TSV настоящим C CLI --strict;
   проверять counts/bytes/latency и то, что каждая задержка кратна 1000 мкс.
3. Отдельный Linux CI на официальном nginx-контейнере: nginx -t, старт на loopback,
   несколько синтетических HTTP-запросов, настоящий лог → адаптер → C.
   Фиксировать nginx -v и digest использованного образа. Тег/конкретный digest
   уточняется при реализации; новая зависимость проекта не добавляется.
4. Полный набор, русская документация, GREEN-коммит. Локально Docker не ставится.
   До успешного контейнерного CI фактическая проверка синтаксиса Nginx не заявляется.

QA независимо согласовал контракт. Ведущий агент утвердил строгий режим,
удаление query после полной проверки URI и ограничение полного URI 2048 ASCII.
Независимая исполняемая матрица проверила 60 случаев; контейнерное CI-задание
использует официальный nginx:stable-alpine и сохраняет фактический digest.
