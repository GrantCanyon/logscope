# JSON v1

Корневой объект содержит `schema_version: 1`, `tool_version`, `settings`, `incident`,
`baseline`, `comparison`, `alerts`. `baseline` и `comparison` равны null, если
сравнение не запрошено. Порядок полей не является частью контракта.

Все целые счётчики — JSON numbers в диапазоне uint64. Потребителю нужен
целочисленный парсер без потери точности (например, стандартный Python `json`).
JavaScript `JSON.parse` преобразует числа в Number и может исказить значения выше
`2^53-1`. Средние, проценты и отношения — десятичные double; сравнивайте их с допуском.
NaN и Infinity не выдаются. Неопределённые метрики представлены null.

## Состояние периода: incident и baseline

| Раздел | Поля и смысл |
|---|---|
| `summary.requests` | Число принятых после фильтров запросов |
| `summary.errors_5xx` | Число кодов 500..599 |
| `summary.bytes` | Сумма байтов |
| `summary.error_rate_pct` | Процент 5xx, null для пустой выборки |
| `summary.first_ms`, `last_ms` | Минимальная/максимальная отметка, null для пустой выборки |
| `summary.status_codes` | Только встречавшиеся коды, строковые ключи `"200"` и т. п. |
| `summary.latency_us` | `sum`, `min`, `max`, `mean`, `p50`, `p95`, `p99` |
| `input` | Учёт всех входных строк и причин отклонения |
| `top_requests`, `top_errors` | Ограниченные списки конечных точек |
| `window` | Сохранённые минуты по времени события |

`latency_us.sum` для пустой выборки равна 0; остальные метрики задержки — null.
Непустая квантиль имеет вид `{"lower":512,"upper":1023}`: обе границы включительны.

### Учёт ввода

`input.lines = input.valid + input.rejected`;
`input.valid = input.filtered + input.accepted`;
`input.accepted = summary.requests`.

`reasons` содержит только ненулевые счётчики машинных причин:
`columns`, `number`, `method`, `target`, `status`, `latency`, `line_too_long`, `binary`.
Одна строка получает одну причину. Слишком длинная строка имеет приоритет над NUL;
для прочих ошибок порядок проверок задан парсером. `samples` — до восьми объектов
`{"line":2,"reason":"columns"}`. Нумерация с 1; исходный текст не включается.

### Конечные точки

```json
{"method":"POST","target":"/checkout","lower":120,"upper":127,"error":7}
```

`lower=upper-error`. Границы относятся к истинному числу запросов с этим ключом
в потоке соответствующей структуры. `top_errors` видит только 5xx. Количество
строк ограничено `min(settings.top, settings.capacity)`. При равных верхних
границах порядок лексикографический: метод, затем target.

### Окно

`capacity_minutes` — W; `outside_window` — слишком старые при поступлении записи;
`evicted_requests` — запросы из позже вытесненных корзин. `buckets` содержит
отсортированные объекты:

```json
{"minute":29453760,"requests":100,"errors_5xx":20,"latency_sum_us":350000,"error_rate_pct":20}
```

`minute` — целая минута Unix, не миллисекунды; для начала минуты умножьте на 60000.
Отсутствующая минута в сохранённом диапазоне означает нулевое число принятых событий.
Отсутствующая минута за пределами окна не означает отсутствия событий во входе.

## Сравнение

- `request_ratio`: `incident.requests / baseline.requests`; null при пустой базе.
- `error_rate_delta_pp`: разность процентов 5xx; null, если любой период пуст.
- `mean_latency_ratio`: отношение средних; null при пустом периоде или нулевой
  средней задержке базы. При нулевой средней инцидента и ненулевой базы равно 0.

Длительность периодов не нормализуется. `--from`, `--until` и прочие фильтры
одинаковы для обоих файлов.

## Сигналы и параметры

`alerts` — список минут, удовлетворяющих правилу из SPEC.md. Каждая запись содержит
`minute`, `requests`, `errors_5xx`, `error_rate_pct`, `rule: "elevated_5xx"`.
Пустой список не доказывает отсутствия сбоя, в особенности за пределами окна.

`settings`: `capacity`, `top`, `window_minutes`, `keep_query`,
`alert_min_requests`, `alert_rate_pct`. Для воспроизводимости сохраняйте также
команду запуска и сведения о входных файлах: полный список фильтров и имена файлов
в этой версии отчёта не сохраняются.
