# Архитектура и инварианты

## Поток обработки

```text
FILE / stdin → фиксированный блок чтения → ограниченная строка → Record
  → проверка фильтров → точные агрегаты
                     → Space-Saving по трафику
                     → Space-Saving по 5xx
                     → кольцо минут по времени события
  → текстовый либо JSON-отчёт → необязательный HTML-компаньон
```

`main.c` отвечает за параметры, выделение/освобождение состояния и коды завершения.
`reader.c` читает двоичные блоки по 65536 байт, собирает строку ограниченной длины,
пропускает её остаток после превышения лимита и возобновляет работу после LF.
Встроенный NUL распознаётся до передачи строки парсеру. Поэтому `strlen` внутри
парсера не может скрыть хвост корректно прочитанной записи.

`parse.c` не использует `atoi`/`strtoull`: проверка каждой цифры исключает знаки,
пробелы, locale-зависимость и переполнение. Условие перед `n = n*10+digit`:

```text
n <= (UINT64_MAX - digit) / 10
```

После проверки запись существует только до следующего обновления агрегатов.
Фильтры проверяются на исходном target, затем query при необходимости удаляется.
Неправильные строки учитываются раньше фильтров: неверный статус не может спрятать
ошибку за фильтром времени или метода.

## Точные агрегаты

`stats.c`: один `Stats` содержит счётчики, 600 ячеек кодов HTTP и 65 корзин задержек.
Перед обновлением проверяются количество запросов, сумма байтов и сумма задержек.
Остальные счётчики ограничены числом запросов, поэтому отдельно переполниться при
соблюдении инварианта не могут. Изменение `Stats` при отказе не производится.

Обновление всех структур анализа целиком не является транзакцией: если следующая
структура отказала, прежние обновления не откатываются. Это безопасно для принятого
контракта: процесс сразу завершает анализ и не выдаёт отчёт по частичному состоянию.
Публичный поток проходит через валидатор; внутренние функции ядра не являются
универсальным API для произвольных, уже повреждённых структур.

### Квантили

Корзина 0 хранит нулевую задержку. Корзина i>0 содержит `[2^(i-1), 2^i-1]`.
Число корзин фиксировано, обновление занимает не более 64 сдвигов.
Для перцентиля p используется ближайший ранг `ceil(n*p/100)`; чтобы не переполнить
`n*p`, он вычисляется как:

```text
(n / 100) * p + ((n % 100) * p + 99) / 100
```

Накопленная частота определяет корзину ранга. Выход — её границы. Это гарантированное
содержание, а не обещание малой абсолютной погрешности. Для задержки 1000 мкс
интервал `[512, 1023]` корректен; для сравнений близких распределений такой точности
может не хватить.

## Space-Saving без роста памяти

Каждый из двух `Top` содержит K слотов ключей, таблицу `2K+1` цепочек и минимальную
кучу индексов. Строки ключа находятся внутри слота; после запуска новые ключи
не требуют malloc. Хеш включает метод, нулевой разделитель и target; сравнение
ключей всегда полное, поэтому коллизия не смешивает разные конечные точки.

Три случая обновления:

1. Ключ уже отслеживается: увеличить `count`, опустить его в минимальной куче.
2. Есть свободный слот: записать `count=1`, `error=0`, поднять слот в куче.
3. Список полон: взять минимум `m`, удалить старый ключ из цепочки,
   заменить новым с `count=m+1`, `error=m`, восстановить кучу.

Для присутствующего ключа истинное число вхождений лежит в `[count-error, count]`.
Сумма верхних границ всех K слотов равна числу обновлений этой структуры. Ключ,
отсутствующий в полном списке, не мог встретиться больше текущего минимального
счётчика. Отображение `--top N` показывает только N строк, поэтому сумма **видимых**
верхних границ не обязана равняться общему числу запросов.

Позиция слота в куче хранится в слоте; обмен меняет обе обратные ссылки. При равных
частотах минимум определяется индексом слота, а финальное отображение — частотой,
затем методом и target. Повтор одного потока даёт тот же результат. Перестановка
строк может изменить приближённые top: алгоритм не обещает независимость от порядка.

Ожидаемая цена: O(длина ключа + log K). В худшем случае преднамеренных коллизий
цепочка может иметь K элементов. FNV-1a выбран ради простоты и воспроизводимости;
это не защита от злоумышленника.

## Окно времени событий

Номер минуты `timestamp_ms / 60000`. Слот — `minute % W`; в нём хранится также
сам номер минуты. Максимальный номер, встреченный у принятой записи, задаёт конец
окна. Минута принимается в кольцо, если `latest-minute < W`.

При продвижении времени на d минут очищается `min(d,W)` слотов. Большой скачок
не вызывает цикл длиной d. Запоздалые события в сохранённом интервале обновляют
корзины, за его пределами увеличивают `outside_window`. Очистка корзины переносит
её объём в `evicted_requests`.

Инвариант после успешного анализа:

```text
accepted = сумма запросов в сохранённых корзинах + evicted_requests + outside_window
```

Время старой записи не вычитается из более новой без проверки порядка, а номер
минуты не превышает `UINT64_MAX/60000`; это оставляет запас для обхода кольца.
Сигналы анализируются только в сохранённых корзинах. Общие итоги и top не очищаются.

## Ресурсы и вывод

Для одного периода память приблизительно:
`2 × K × sizeof(TopEntry)` + таблицы/кучи + `W × sizeof(Minute)` + `Stats`.
При сравнении удерживаются два состояния; чтение остаётся последовательным.
Сортировка отчёта использует ещё K указателей. Входные буферы фиксированы.
Память O(K + W), без зависимости от числа строк N и общего числа ключей D.

Отчёт начинается лишь после успешного завершения обоих периодов. JSON-строки
экранируют кавычки, обратные слеши и чувствительные HTML-символы; числа uint64
печатаются как целые. При ошибке stdout/flush процесс возвращает код 2; уже
записанные байты откатить нельзя. Сбой анализатора до отчёта оставляет stdout пустым.

HTML строится отдельно стандартной библиотекой Python: целые не проходят через
JavaScript Number, текст экранируется, SVG создаётся из числовых агрегатов,
CSP запрещает внешние ресурсы. Это отчёт по ограниченному JSON, а не обработка
исходного многогигабайтного журнала браузером.

## Что проверено и что требует отдельного решения

Тесты сопоставляют top с точным независимым `Counter`, проверяют все показанные
интервалы и ограничение пропущенных ключей. Контракты ввода охватывают граничные
значения, NUL, слишком длинные строки и восстановления на границе блока.
HTML проверяется на вредоносной строке и максимальном uint64.

Проверки распределителя при искусственном отказе malloc, доказательство отсутствия
всех возможных ошибок и устойчивость к намеренной нагрузке не заявляются.
Для публичного сетевого сервиса понадобились бы иной threat model, ограничения
ресурсов ОС и вероятно другой хеш; текущий инструмент работает локально.
