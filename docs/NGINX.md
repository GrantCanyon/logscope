# Профиль LogScope JSON v1 для Nginx

Этот адаптер принимает **один документированный профиль**, а не произвольный
«Nginx JSON»: Nginx позволяет самостоятельно задавать log_format. Поддержка
escape=json описана в [официальной документации](https://nginx.org/en/docs/http/ngx_http_log_module.html#log_format).
Используется исходный `$request_uri` с аргументами и `$body_bytes_sent` без
заголовков ответа, согласно [описанию переменных](https://nginx.org/en/docs/http/ngx_http_core_module.html#variables).

## Настройка профиля

Точное определение: [examples/nginx/logscope-json.conf](../examples/nginx/logscope-json.conf).
Оно должно находиться в контексте `http`. Для нужного `server` или `location`
используется, например:

```nginx
access_log /var/log/nginx/logscope.jsonl logscope_json_v1;
```

Это пример настройки, а не команда автоматического изменения работающего сервера.
Конфигурацию сначала проверяют `nginx -t`; приложение само не меняет Nginx.

Каждая физическая строка — JSON-объект ровно с шестью **строковыми** значениями:

```json
{"msec":"1767225600.123","request_method":"GET","request_uri":"/api?source=synthetic","status":"200","body_bytes_sent":"42","request_time":"0.123"}
```

Порядок ключей неважен. Отсутствующие, повторные и дополнительные ключи,
JSON numbers, null, bool и вложенные значения отклоняются. Пустые значения и `-`
не превращаются в ноль. Этот профиль намеренно строже произвольной JSON-записи.

## Сначала преобразование, затем анализ

Предпочтителен двухшаговый процесс: успешное преобразование проверяется **до**
анализа TSV. Например, Bash в существующем каталоге build:

```bash
tsv=$(mktemp build/nginx.XXXXXX.tsv) || exit 2
if python scripts/nginx_to_tsv.py access.jsonl > "$tsv"; then
    ./build/logscope analyze "$tsv" --strict --json > build/nginx-report.json || exit $?
else
    echo "Преобразование неуспешно; частичный TSV не анализируется." >&2
    exit 1
fi
```

Пример также передаёт ненулевой код C-анализатора вызывающему процессу.
Временный TSV сохраняется для
проверки; он может содержать частичный результат при ошибке.

Для PowerShell 7.4+ используйте раздельные шаги и явную проверку кода:

```powershell
python scripts/nginx_to_tsv.py access.jsonl > build/nginx.tsv
if ($LASTEXITCODE -ne 0) { throw 'Преобразование неуспешно; TSV не анализируется.' }
./build/logscope.exe analyze build/nginx.tsv --strict --json > build/nginx-report.json
if ($LASTEXITCODE -ne 0) { throw 'Анализ неуспешен; отчёт нельзя считать готовым.' }
```

В старом Windows PowerShell текстовое перенаправление может менять кодировку.
Для сохранения ASCII TSV используйте перенаправление через cmd:

```powershell
cmd /c "python scripts\nginx_to_tsv.py access.jsonl > build\nginx.tsv"
if ($LASTEXITCODE -ne 0) { throw 'Преобразование неуспешно.' }
```

Если нужен прямой Bash-конвейер, включите `pipefail`:

```bash
set -o pipefail
python scripts/nginx_to_tsv.py access.jsonl | ./build/logscope analyze - --strict --json > build/nginx-report.json
status=$?
if [ "$status" -ne 0 ]; then
    echo "Один из участников конвейера завершился с ошибкой; отчёт не принимать." >&2
    exit "$status"
fi
```

Без проверки обеих сторон C может успешно обработать корректный префикс, когда
адаптер уже остановился на повреждённой записи. PowerShell не приписывается
поведение Bash pipefail: для него рекомендованы отдельные шаги выше.

## Время и единицы

В профиле секунды имеют каноническую форму `0.000` или ненулевую целую часть
и ровно три цифры после точки. Знаки, экспонента, пробелы, запятая и ведущие нули
не принимаются. Адаптер не использует float: `1.234` секунды дают 1234 мс,
`0.123` секунды задержки — 123000 мкс. Каждая выходная задержка кратна 1000 мкс;
новой точности при смене единиц не появляется.

`$msec` отражает момент записи журнала, а `$request_time` — длительность запроса
с миллисекундным разрешением; это не время начала запроса и не только время
upstream. [Семантика Nginx](https://nginx.org/en/docs/http/ngx_http_log_module.html#log_format).
Выходные отметки ограничены uint64, задержки — 24 часами, статус — 100..599.

## Политика URI и ограниченная память

Весь декодированный JSON URI сначала проверяется: 1..2048 видимых ASCII-символов,
начало `/` либо ровно `*`. Управляющие символы, NUL, tab, CR/LF, DEL, Unicode
и суррогаты отклоняются, даже если находятся в query. Процентное декодирование
не выполняется: буквальный `%0A` остаётся строкой из трёх символов.

По умолчанию query удаляется **адаптером до вывода TSV**. Это уменьшает количество
чувствительных значений в промежуточных файлах, но не обезличивает сам путь.
Сохранение query требует `--keep-query` адаптера; для сохранения при группировке
также нужен `--keep-query` C CLI. Удалённый query ядро восстановить не может.
Слишком длинный полный URI отклоняется, даже если после удаления query был бы короче.

JSON-строка ограничена 16384 байтами без окончания LF/CRLF. Последняя строка может
быть без LF; одиночный CR недопустим. Пустой файл корректен, пустая строка — нет.
Чтение и пропуск слишком длинной строки используют ограниченные блоки. Память
не растёт с длиной файла или повреждённой строки; глубоко вложенный JSON и тысячи
цифр приводят к контролируемому отказу, а не traceback.

## Ошибки

По умолчанию первая ошибка данных прекращает обработку. `--skip-invalid` выдаёт
корректные строки после повреждённых, но итоговый код при любых отклонениях — 3.
На stderr попадают не более восьми номеров строк с кодами причин и сводные счётчики;
исходные строки, URI, значения полей, пути и тексты исключений не выводятся.

| Код | Значение |
|---:|---|
| 0 | Все записи успешно преобразованы |
| 1 | Ошибка параметров |
| 2 | Ошибка чтения/записи, включая закрытый downstream |
| 3 | Ошибка данных или лимита, в том числе в режиме --skip-invalid |

Ошибка ввода/вывода имеет приоритет над кодом 3. Уже выданные строки не отзываются.
Сбой выходного канала возвращает ровно 2: повторный flush Python не должен
подменять его кодом 120. Эти случаи проверяются отдельными процессами.

## Проверка настоящего Nginx

В CI добавлено отдельное Linux-задание: официальный образ `nginx:stable-alpine`,
`nginx -t`, запуск только на loopback, шесть синтетических HTTP-запросов,
полученный журнал → адаптер → C CLI. Проверяются числовые строки, методы, статусы,
байты тела, точная сумма задержек и отсутствие query в TSV. Версия Nginx и digest
образа сохраняются с синтетическими свидетельствами в артефакт CI.

Тег образа может обновляться; результат относится к digest конкретного запуска.
Docker не нужен для использования адаптера и не устанавливается локальными
скриптами. Реальная конфигурация проверена в
[CI 41365469742](https://github.com/GrantCanyon/logscope/actions/runs/41365469742)
для коммита `39b00389edafc6eb88441f3a58968debbaa6e57b`: Nginx 1.30.6,
образ `nginx@sha256:0e52bd054126cdc040b1276c0af347aeb02a41b9cfe305d6094767ac30e97949`.
В скачанном артефакте подтверждены шесть синтетических запросов и нулевые коды
адаптера/C. Это проверка в Linux CI; локальный Docker не запускался.
Пример для самостоятельного повторения — в [сквозном разборе](walkthrough.md).
