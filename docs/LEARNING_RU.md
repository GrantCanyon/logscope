# Как самостоятельно разобрать и проверить LogScope

Этот материал рассчитан на читателя, который знает переменные, циклы, функции
и указатели C, но ещё не строил потоковый анализатор. Цель — понимать компромиссы
и проверять результат, а не только успешно запустить пример.

## 1. Начните с данных и единиц

Создайте синтетический пример командами из README. У записи три разные числовые
величины: время события в миллисекундах, длительность запроса в микросекундах
и размер ответа в байтах. Смешение первых двух даст правдоподобный, но неверный
график. Откройте несколько строк `build/demo/incident.tsv`, затем найдите их
поля в `Record` из `src/logscope.h`.

Генератор моделирует 90 минут, всплеск ошибок оплаты между 45-й и 55-й минутами,
редкие запоздавшие события и отдельный спокойный период. Это сконструированный
сценарий, не статистическая модель реального сервиса. `truth.json` считает итоги
при создании записей; тест сравнивает их с результатом C-программы.

**Упражнение:** две записи с задержками 100 и 900 мкс. Среднее равно 500 мкс,
p50 ближайшего ранга равно 100 мкс. Интервал гистограммы для p50 — `[64,127]`.
Не заменяйте среднее квантилью: они отвечают на разные вопросы.

## 2. Почему чтение отделено от разбора

Одна строка может быть длиннее блока чтения и даже намеренно не содержать LF.
Если накапливать её в растущем буфере, утверждение об ограниченной памяти станет
ложным. `reader.c` сохраняет только фиксированный префикс и продолжает искать
конец строки, отмечая `long_line`. Следующая корректная запись после LF не теряется.

Парсер получает уже завершённую C-строку. NUL нельзя отдавать ему без проверки:
`strlen` закончит чтение раньше фактического конца записи. Поэтому обнаружение
нулевого байта — обязанность читателя. Затем парсер проверяет грамматику полей.

**Упражнение:** добавьте пустую строку между двумя корректными. В обычном режиме
должно остаться два принятых запроса и одна ошибка `columns`. В строгом режиме
код завершения 3, stdout пуст, сообщение указывает строку 2.

## 3. Проверяем арифметику до изменения состояния

Беззнаковое переполнение в C определено по модулю `2^64`, то есть программа может
тихо выдать ноль после очень большого числа. Нам это не подходит. До `sum += value`
проверяем `sum > UINT64_MAX-value`. Сначала проверяются все потенциально опасные
поля `Stats`, только затем изменяется структура.

Посмотрите `stats_contract` в `tests/unit.c`: проверка сравнивает всю структуру
до и после отказа. Это тест поведения, а не проверка наличия нужной строки в коде.
Внешний тест отправляет две записи, суммарный размер которых больше uint64,
и требует отсутствия отчёта.

## 4. Зачем приближённые конечные точки

Точный словарь по каждому пути растёт с количеством различных URL. На миллионах
уникальных ключей он перестаёт удовлетворять требованию фиксированной памяти.
Space-Saving заранее выделяет K слотов и при заполнении заменяет минимальный
счётчик. Цена — интервалы вместо точного числа для части ключей.

Разберите вручную поток `/a, /a, /b, /c` при K=2:

| После события | Слоты: верхняя граница и ошибка |
|---|---|
| `/a` | `/a: (1,0)` |
| `/a` | `/a: (2,0)` |
| `/b` | `/a: (2,0)`, `/b: (1,0)` |
| `/c` | `/a: (2,0)`, `/c: (2,1)` |

Истинная частота `/c` равна 1 и содержится в `[1,2]`. Верхняя оценка 2 не означает,
что `/c` действительно встретился дважды. Именно поэтому отчёт показывает границы.
Два независимых списка нужны, потому что редкий, но постоянно падающий путь может
не попасть в список самых посещаемых.

Теперь изучите `top.c`: хеш-таблица находит ключ, куча быстро выбирает минимум.
`heap_pos` — обратная ссылка из слота в кучу. После обмена в куче надо изменить
обе обратные ссылки, иначе следующее обновление затронет чужую позицию.

**Упражнение:** измените `--capacity 128` на 1 и сравните границы. Общие числа должны
остаться теми же; качество списка конечных точек ухудшится. Тест с Python `Counter`
проверяет интервалы на случайных потоках для нескольких ёмкостей.

## 5. Время события и порядок поступления

В распределённых системах поздняя запись не обязательно описывает позднее событие.
LogScope использует время внутри строки. При W=3 и событиях в минутах 10, 8, 7,
12, 11, 9 итоговое окно — 10..12. Минута 7 и поздно пришедшая 9 оказались вне окна;
ранее сохранённая 8 вытеснена. Всего запросов 6, в окне 3, вытеснен 1, вне окна 2.

**Упражнение:** переставьте строки и проверьте общие итоги. Они сохранятся,
но счётчики `outside_window` и `evicted_requests` могут измениться: они описывают
историю поступления. Сохранённые агрегаты последних W минут должны соответствовать
принятым в это окно событиям.

## 6. Как читать сигналы без лишних выводов

20 ошибок из 100 запросов дают 20%, но 1 ошибка из 1 запроса даёт 100%. Минимальный
объём отсеивает такие малые минуты. Сравнение с базой требует и относительного,
и абсолютного роста: ≥3 раз и ≥5 процентных пунктов. При базе 1% и инциденте 20%
оба требования выполняются; при базе 50% — нет.

Это эвристика, не p-value и не доказательство сбоя именно в приложении. Повышенная
доля 5xx может отражать изменение маршрутизации, состава клиентов или самой
выборки. При фильтре только 5xx доля равна 100% по определению — нельзя делать
из неё вывод о доле ошибок во всём трафике.

## 7. Проверки, которые способны находить ошибки

Запустите полный набор из README. Сначала читайте тест как контракт, затем код.
Для каждого теста спросите: какая реальная ошибка заставит его упасть?

- Потеря байта после границы блока нарушит число принятых строк.
- Неверный знак сравнения `--until` пропустит правую границу.
- Забытое увеличение `error` при замене нарушит интервал Space-Saving.
- Прямое включение target в HTML позволит тегу стать разметкой.
- Случайное преобразование uint64 в float исказит максимум `18446744073709551615`.

На Linux запустите сборку с `--sanitize` и повторите тесты. ASan находит доступ
за границы памяти, UBSan — некоторые виды неопределённого поведения. Успешный
запуск не является доказательством отсутствия всех ошибок, но проверяет конкретные
исполненные пути. CI содержит эти задания; факт их прохождения смотрите в запусках CI.

## 8. Как честно измерять производительность

`benchmark.py` генерирует данные до замера, один раз прогревает процесс/кэш,
затем измеряет несколько независимых запусков. Каждый отчёт сверяется с точными
контрольными числами. В измерение входят запуск процесса, чтение, анализ и JSON.
Сохраняются все длительности, медиана и пик памяти каждого процесса.

Число запросов в секунду для 10 тысяч строк хуже, чем для миллиона: фиксированные
затраты запуска сильнее влияют на малую выборку. Почти постоянная память при росте
файла согласуется с конструкцией алгоритма, но три точки графика сами по себе
не доказывают ограниченность памяти — это следует из структуры выделений.

Для продолжения полезнее добавить независимый контракт на новое требование,
чем усложнять алгоритм заранее. Например, точные квантили потребуют другого
компромисса между памятью и точностью; это изменение спецификации, а не косметика.
