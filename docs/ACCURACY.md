# Точность, ёмкость и память Space-Saving

[Автономный HTML](../examples/accuracy.html) · [Полные результаты JSON](../examples/accuracy.json)

Эксперимент отвечает на вопрос: что меняется, если разрешить потоковому анализатору
хранить больше конечных точек? Он проверяет уже существующий C CLI и не меняет
алгоритм. Сравнивать только скорость было бы недостаточно: маленький sketch может
быстро обработать файл, но плохо восстановить верхнюю часть длинного почти
равномерного распределения.

## Повторение

```bash
python scripts/build.py --cc gcc
python scripts/accuracy.py --requests 100000 --cardinalities 32,256,4096 --capacities 16,64,256,1024 --top-k 10 --seed 2026 --repeats 3 --compiler-description "GCC: укажите версию; C17 -O2" --output build/accuracy.json
python scripts/render_accuracy.py build/accuracy.json --output build/accuracy.html
```

Для Windows укажите `--binary build/logscope.exe`, если бинарник лежит не по
умолчанию. Нужна только стандартная библиотека Python. Возможные размеры capacity
ограничены диапазоном CLI 1..4096. Необязательно повторять большую матрицу для
проверки установки: достаточно 200 строк, двух ёмкостей и одного повтора.

## Что именно сравнивается

Для каждого заданного числа возможных товарных путей создаётся **один** файл
существующим генератором инцидента. Все ёмкости читают идентичные байты, один seed
и одинаковую последовательность строк; SHA256 сохраняется у набора и каждой точки.
Контрольный Counter независимо читает TSV, объединяет query и сохраняет метод
как часть ключа. Счётчики всех запросов и 5xx раздельны.

`requested_cardinality` не равна фактическому D: генератор также создаёт /checkout,
а на малом входе некоторые возможные пути могут не встретиться. D определяется
исходным файлом, а не параметром генератора или числом слотов C.

CLI запускается с `--top capacity`, поэтому валидатор получает весь sketch.
Каждый прогрев и измеренный запуск проверяются:

- все показанные ключи действительно встречались и уникальны;
- `lower <= Counter[key] <= upper`, `error=upper-lower`;
- сумма upper равна объёму соответствующего потока;
- истинная частота каждого пропущенного ключа не больше минимального upper
  полного sketch; неполный sketch не имеет права терять положительные ключи;
- при capacity>=D представлены все ключи и все границы точны;
- общие запросы, 5xx, байты и сумма задержек совпадают с независимым эталоном.

Любое нарушение прекращает эксперимент с ненулевым кодом; неуспешная точка
не публикуется как «почти 100% покрытия». Пустой поток 5xx корректен: границ нет,
recall равен null. При сбое новый успешный JSON не записывается; прежний файл по
тому же пути не удаляется, поэтому всегда проверяйте код завершения команды.

## Почему recall представлен диапазоном

Точный top-k неоднозначен, если несколько ключей на границе имеют равные частоты.
Произвольно выбрать один такой ключ и объявить остальные ошибкой — нечестная оценка.

Пусть m=min(k,D), tau — m-я наибольшая частота, H — обязательные ключи с частотой
выше tau, E — ключи с частотой tau. Нужно выбрать q=m-|H| ключей из E. В первых k
строках результата найдено h ключей H и e ключей E. Тогда возможное совпадение:

```text
recall_lower = (h + max(0, e - (|E| - q))) / m
recall_upper = (h + min(e, q)) / m
```

Верхняя граница оптимистическая: лучшее допустимое разрешение ничьей. Нижняя —
худшее допустимое. Это **не доверительный интервал** и не вероятность правильности.
При capacity<k знаменатель остаётся m, а не уменьшается до числа слотов.

Пример: точные частоты a=2,b=1,c=1, k=2. Результат a,b имеет recall от 1/2 до 1:
допустимы оба точных top — a,b и a,c. Все частоты могут быть совершенно точными,
хотя диапазон recall широк. Поэтому отчёт отдельно показывает среднюю/максимальную
ширину частотных интервалов и долю **отслеживаемых** ключей с точной частотой.
Эта доля не характеризует все ключи входа.

## Наблюдения в опубликованном запуске

Фактически измерено 2 ноября 2026 года на Windows 11, Intel i5-13420H,
Zig 0.17.0 `cc -O2`, Python 3.12.14. По 100000 строк на набор, seed 2026,
один прогрев и три повтора для каждой из 12 точек. Полные длительности, диапазоны
RSS, версия окружения, параметры и SHA256 бинарника находятся в JSON.

| Фактическое D, все запросы | Capacity | Recall top-10 | Максимальная ширина частотного интервала |
|---:|---:|---:|---:|
| 33 | 16 | 30–30% | 5326 |
| 33 | 64 | 100–100% | 0 |
| 257 | 64 | 10–10% | 1268 |
| 257 | 256 | 90–100% | 278 |
| 257 | 1024 | 90–100% | 0 |
| 4097 | 16 | 10–10% | 5327 |
| 4097 | 1024 | 10–10% | 77 |

При D=257 capacity=256 оставляет интервальную неопределённость, хотя оптимистическая
оценка top-10 уже достигает 100%. При capacity=1024 все частоты точны; оставшийся
диапазон 90–100% вызван ничьей, а не ошибкой sketch.

В наиболее разнообразном потоке recall по всем запросам остаётся 10% даже при
capacity=1024, несмотря на снижение максимальной ширины интервала с 5327 до 77.
Это не нарушение гарантии Space-Saving: возможность ограничить частоту пропущенных
ключей не означает точное ранжирование похожих частот длинного хвоста.
Для потока 5xx того же набора recall вырос с 10–30% до 70–100%; его распределение
и фактическое D=716 отличаются от общего потока.

Из `sum(upper)=N` и K заполненных слотов следует `min(upper)<=N/K`. Поэтому ключ
с истинной частотой **больше N/K** не может быть пропущен. Это полезная гарантия
для тяжёлых ключей, но она не обещает найти любой top-k независимо от распределения.

## Время и память: наблюдения, а не подогнанная кривая

Таймер измеряет только отдельный C-процесс: запуск, чтение, анализ и JSON.
Генерация, Counter, проверка отчёта и HTML исключены. Память Python-эталона
может расти с D и не включается в заявленную память C-анализатора.
На Windows используется PeakWorkingSetSize, на Unix — wait4 ru_maxrss отдельного
процесса с приведением платформенных единиц к байтам.

В данном запуске медианы времени лежат примерно в диапазоне 135–161 мс.
Для D=4097 наблюдаемый пик памяти вырос примерно с 5,05 МиБ при capacity=16
до 8,11–8,16 МиБ при capacity=1024. Однако при D=33 измеренный RSS для capacity=1024
оказался ниже, чем для capacity=256. Такие точки сохранены без исправления:
RSS включает базовый процесс и окружение и не равен теоретической сумме выделений.

Порядок ёмкостей детерминированно перемешан в каждом раунде и записан в JSON.
Кэш прогрет; холодный диск, сеть и параллельная нагрузка не измеряются.
Монотонность времени, RSS или recall для каждого конечного набора не гарантируется.
Повтор должен воспроизвести входной hash и метрики точности при той же версии
генератора/Python; длительности и память могут отличаться.

## Проверка самого эксперимента

Ручные fixtures охватывают точный sketch, вытеснения, capacity<k, k>D, полную ничью,
пустую серию 5xx, разные методы/query и намеренно испорченные границы.
Независимый QA дополнительно сравнил 6686 случаев recall с полным перебором всех
допустимых точных top-k множеств, отверг четыре повреждённых отчёта и проверил
12 малых sketch через настоящий C CLI. Числовых расхождений не обнаружено.

В CI выполняется малый воспроизводимый smoke-эксперимент без порогов скорости
и памяти. Большая таблица — сохранённый фактический запуск; её наличие само по себе
не означает, что новый коммит уже прошёл удалённые проверки.
