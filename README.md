# LogScope

**Потоковый анализ HTTP-журналов на C17: точные итоги, ограниченная память,
объяснимые сигналы и автономный отчёт.**

LogScope помогает ответить на конкретные вопросы после инцидента: выросла ли доля
5xx, какие конечные точки сосредоточили ошибки, в какие минуты происходил всплеск,
как изменились задержки относительно базового периода. Он читает файл один раз,
не хранит строки целиком и явно показывает границы приближённых оценок.

Проект самостоятельный: парсер, проверяемая арифметика, Space-Saving с хеш-таблицей
и минимальной кучей, кольцевое окно времени событий и формирование JSON написаны
на стандартном C17. Python нужен только для проверок, синтетических данных,
HTML и измерений. Анализатор не требует сторонних библиотек или сети.

## Быстрый запуск

Нужны Python 3.10+ и компилятор C17 — GCC, Clang или `zig cc`.

```bash
python scripts/build.py --cc gcc
python scripts/build.py --cc gcc --unit
./build/unit
python -m unittest discover -s tests -v

python scripts/generate.py --output build/demo --requests 100000
./build/logscope analyze build/demo/incident.tsv --baseline build/demo/baseline.tsv
./build/logscope analyze build/demo/incident.tsv --baseline build/demo/baseline.tsv --json > build/report.json
python scripts/render_html.py build/report.json --output build/report.html
```

Откройте `build/report.html` в браузере. Это один файл с графиком, таблицами,
сравнением периодов и описанием ограничений. В нём нет JavaScript, внешних шрифтов,
сетевых запросов и зависимостей. В GitHub HTML доступен как файл для скачивания.

Windows: используйте `build/logscope.exe`, `build/unit.exe`; пример компилятора:
`python scripts/build.py --cc "C:/tools/zig/zig.exe cc"`. PowerShell 7 сохраняет
перенаправленный JSON в UTF-8. Для старого Windows PowerShell используйте
`cmd /c "build\logscope.exe analyze build\demo\incident.tsv --json > build\report.json"`.
Справка программы и отчёты используют UTF-8; при неверном отображении настройте
кодировку терминала. Скрипты не скачивают и не устанавливают компилятор.

Дополнительные варианты сборки:

```bash
make test CC=clang
cmake -S . -B build/cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build/cmake
ctest --test-dir build/cmake --output-on-failure
```

## Формат журнала

Шесть полей, настоящая табуляция между ними, без заголовка:

```text
1767225600000	GET	/catalog/item/42?campaign=synthetic	200	2400	18500
1767225600010	POST	/checkout	503	160	950000
```

| Поле | Смысл |
|---|---|
| `epoch_ms` | Время события, миллисекунды Unix UTC |
| `METHOD` | 1..16 заглавных ASCII-букв |
| `request_target` | Путь с query, до 2048 видимых ASCII-символов; `/…` или `*` |
| `status` | HTTP-код 100..599 |
| `response_bytes` | Беззнаковый uint64 |
| `latency_us` | Задержка в микросекундах, максимум 24 часа |

Apache/Nginx combined и произвольный JSON напрямую не принимаются. Для реальных
журналов нужен отдельный экспорт в этот строгий формат. Это осознанная граница
проекта: разбор проверяемого формата не выдаётся за универсальный импортёр.

## Типичные расследования

```bash
# Ошибки API после указанного времени; фильтры применяются одновременно
./build/logscope analyze access.tsv --from 1767225600000 --status 500:599 --path-prefix /api

# Медленные запросы POST, отдельные ключи с query
./build/logscope analyze access.tsv --method POST --min-latency-us 500000 --keep-query

# Больше отслеживаемых ключей и окно за сутки
./build/logscope analyze access.tsv --capacity 1024 --top 25 --window-minutes 1440

# Строгий режим: первая повреждённая строка прекращает анализ
./build/logscope analyze access.tsv --strict --json
```

При фильтре `--status 500:599` доля 5xx относится к **отфильтрованной** выборке
и закономерно равна 100%. Для оценки общей доли ошибок такой фильтр не нужен.
`--from` включителен, `--until` исключителен. Query удаляется после проверки
`--path-prefix`; метод остаётся частью ключа, поэтому GET и POST не смешиваются.

## Что можно считать точным

- Количество, байты, коды HTTP и сумма задержек точны до переполнения uint64;
  переполнение останавливает анализ, а не молча обнуляет счётчик.
- p50/p95/p99 — интервалы, содержащие квантиль ближайшего ранга. Например,
  `[32768, 65535]` мкс не означает точный p95 в 65535 мкс.
- Для top показаны нижняя и верхняя границы количества. При достаточной ёмкости
  они совпадают; после вытеснений ранжирование приближённое.
- Кольцо хранит последние W минут по максимальному встреченному времени события.
  Слишком старые записи входят в общие итоги, но не в график и сигналы.
- Сигналы — эвристика по объёму и доле 5xx. Они не доказывают причину сбоя.
- Отношение количества запросов к базовому периоду не учитывает длительность
  периода и не является сравнением запросов в секунду.

## Проверки и измерения

Тесты используют реальные процессы и независимые счётчики Python: переполнения,
повреждённые строки, NUL, границы буферов, случайные потоки с точным эталоном,
вытеснения top, скачки времени, одинаковые фильтры, сравнение периодов, экранирование
HTML и воспроизводимость генератора. Отдельно проверяются ошибки устройств Unix.

CI настроен на GCC/Clang Linux с ASan/UBSan, Clang Windows/macOS и CMake.
Локально проверены Zig 0.17.0 на Windows и все применимые тесты. Само наличие
конфигурации CI не означает, что удалённые проверки уже прошли.

В локальном замере 1 000 000 синтетических строк (66,09 МиБ) обработан за медианные
0,752 с; максимальная рабочая память — около 5,06 МиБ при ёмкости 128.
Это результат конкретного ноутбука с прогретым файловым кэшем, не обещание
производительности. [Сырые данные и методика](docs/BENCHMARK.md).

## Границы применения

Это локальный инструмент расследования, не сервер мониторинга. Нет сетевого
приёма, автоматических оповещений, декодирования маршрутов, полнотекстового поиска,
гарантий против намеренно подобранных хеш-коллизий и точных квантилей.
Память анализатора ограничена параметрами, но Python-компаньон читает весь **отчёт**
JSON в память. Конечные точки попадают в отчёт: перед передачей проверьте отсутствие
секретов в путях и особенно в query. Примеры и измерения используют только синтетику.

Коды завершения: `0` успех; `1` параметры; `2` ввод/вывод или память;
`3` строгая ошибка входа или переполнение. После ошибки записи stdout может
содержать незавершённый отчёт; всегда проверяйте код завершения.
